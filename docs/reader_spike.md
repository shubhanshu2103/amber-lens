# Reader spike: vision model vs OCR on 10 tuning photos (#8)

Run 2026-11-24 on a laptop with an RTX 4050 (6 GB VRAM), 16 GB RAM, Windows 11. Everything is local, so
**cost is $0.00 per photo for every arm**. Prompt `nameplate-v3`, temperature 0, fixed seed, JSON-schema
output. OCR is Tesseract 5.4.0 (page segmentation 11, photos upscaled to ~1800 px wide).

**Truth is not yet human-verified.** `labels.csv` was read off the photos by an AI model (its `verified_by` column names
an AI reader and `human_checked` is empty). Every "correct" below means *agreement with AI-read labels*.
A check sheet for a person to verify these 10 rows is generated by `check_sheet.py` (see "Reproduce").

Labels come from the read-only worktree of `d/dataset-hf-40` (`AMBER_DATA_DIR=../amber-lens-data/data`).
When the final `labels.csv` lands on `main`, switch `AMBER_DATA_DIR` to `./data` and rerun.

## Photos

`hf_02, hf_04, hf_06, hf_053, hf_066, hf_069, hf_259, darjja_train_01, darjja_train_10, hf_295`: glare,
small text, an angled plate, blur, a compressor, a transformer, an AC unit, and `hf_295`, which the
labels mark unreadable (no model number). Tuning split only.

## Arms

| Arm | What counts as a reading |
| --- | --- |
| `vision` | the model's answer as is |
| `vision+rule` | kept only if the field's format rule passes (standard voltage set, current range, model number shape, frequency 50/60/400, power has a unit) |
| `vision+rule+located` | also kept only if Tesseract finds the value printed on the photo (the strict READ condition chosen for T2) |
| `ocr` | Tesseract alone, fields pulled out by fixed label patterns |

Scoring compares on a key that ignores case, whitespace, dash style, decimal comma vs point, the field's
own unit word and word-only labeller notes such as "(compressor RLA)". A value where the label says the
field is not printed counts as **extra**, which is as bad as **wrong**: both are wrong READs.

## What we learned

1. **The format rule alone barely helps** (13 -> 12, 9 -> 8 wrong READs). The models' mistakes are
   well-formed values, just the wrong ones.
2. **Every model invents a full plate for an unreadable photo.** On `hf_295` qwen2.5vl:3b returned model
   `R22-1/2E-2501-A`, 400/230 V, 1.0 A, 50 Hz, and qwen2.5vl:7b returned model `822-V TEK-2501`. The
   format rule passes most of these. Requiring the value to be printed where OCR can see it removes all
   of them (0 extra in every located arm). The model cannot be trusted to say "unreadable"; the rule must.
3. **Example values in the prompt get copied.** With prompt v2, qwen2.5vl:7b answered `4.2/2.1 A` on the
   unreadable plate, which was the example in the prompt. v3 contains no digits at all.
4. **Locating is the bottleneck for coverage.** The located arms keep 5 of 30 key values. Tesseract on
   these 200-740 px public photos finds too little text. The strict rule is safe, but at this OCR
   quality most fields would come out DISPUTED.
5. **qwen3-vl:4b (Ollama default tag) is a thinking model.** It ignores `think: false`, writes ~5,000
   characters of reasoning, takes 37 s on average and returned an empty answer on 5 of 10 photos.
6. **Which identifier is "the model number" is a policy question.** On `hf_04` the plate prints MODEL
   `HLS447SR0608` and CAT. NO. `HHI150-12-447T`. The prompt asks for the catalog number; both qwen2.5
   models still read the MODEL field. That is the only wrong READ left for qwen2.5vl:7b after locating.
7. **Short numbers can be located in the wrong cell.** The remaining extra wrong READ for qwen2.5vl:3b is
   `hf_053` current `15A`: the value `15` is printed on the plate, but as the kW rating.

## Recommendation

- **Model: qwen2.5vl:7b** for the reader. It has the fewest wrong READs (9 raw, 1 after locating) and
  the most raw correct values (21 of 30). At ~7 s per photo it is acceptable for a site check. qwen2.5vl:3b
  (2.3 s) stays as the fast fallback and the demo-speed option; the difference after locating is 1 vs 2
  wrong READs on 10 photos, so this choice should be rechecked on all 35 tuning photos in T2.
  Drop qwen3-vl:4b.
- **Strictness: keep the strict rule (decision T2-1 A).** A READ needs a format pass **and** the value
  found on the photo. The format rule alone does not stop invented values; locating does.
- **Raise coverage by improving OCR, not by loosening the rule.** The open question for T2 is how to find
  more of the printed text (see the T1 task report for the decision request).
- **Tighten locating for short numbers:** a rating value of 1-3 characters should only count as located
  on a line that also carries the field's unit or label (for example `A`, `AMPS`, `FLA`).

## Reproduce

```bash
python -m amber_lens.perception.spike --models qwen2.5vl:3b qwen2.5vl:7b qwen3-vl:4b \
    --json-out docs/reader_spike_results.json
python -m amber_lens.perception.check_sheet --results docs/reader_spike_results.json
```

Responses are cached in `.cache/perception/vision/` by image hash, model and prompt version, so a rerun
reproduces these numbers without calling the models (the latencies are the ones measured on the first
call). All readings, labels and run info are in `docs/reader_spike_results.json`.
